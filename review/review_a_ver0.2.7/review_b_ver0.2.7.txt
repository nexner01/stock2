# Stock2 PDD v0.2.7 리뷰

**이전 리뷰(0.2.6)에서 지적한 세 가지가 이번에도 전부 해결됐습니다.**

1. "실패 복구가 브라우저 새로고침뿐이라 FR-16 상태 보존 원칙과 충돌" → 그룹별 `다시 시도` 버튼 신설(FR-12, AC-22). "다른 그룹과 현재 화면 상태를 유지한 채" 복구되도록 명시. 정확히 지적한 방향으로 고쳐짐.
2. "수동 새로고침 vs 브라우저 새로고침 구분 모호" → "사용자는 데이터 그룹별 `다시 시도`를 실행할 수 있으며, 이는 브라우저 전체 새로고침과 구분한다"로 명문화.
3. "2초 주기 기준 6~8초 만에 영구 실패로 전환되는 건 너무 공격적" → 타임아웃(5초)과 주기(2초)를 분리하고 "고정 시각 스케줄" 방식으로 재설계해서, 재시도가 매 주기(2초)가 아니라 "타임아웃 확정 이후 처음 도래하는 고정 조회 시각"에 이루어지도록 바뀜. 기본값 기준 계산 예시(0초, 6초, 12초, 18초 요청 → 23초에 실패 확정)까지 직접 검증해보니 계산이 정확히 맞습니다. 6~8초에서 23초로 완화됐고, 계산식도 재현 가능하게 명시되어 훨씬 견고해졌습니다.

**이번 버전에서 새로 보이는 이슈**

1. **기본 설정 자체가 "타임아웃(5초) > 주기(2초)" 구조라, 정상 상황에서도 회차 건너뛰기가 구조적으로 자주 발생할 수 있습니다.** FR-12에 따르면 이전 요청이 실행 중이면(타임아웃 여부와 무관하게) 다음 고정 조회 시각의 요청은 건너뜁니다. 즉 공급원 응답이 2~5초 사이(타임아웃은 아니지만 주기보다는 긴 경우)면 매번 정상 응답인데도 건너뛰기가 기록됩니다. 그런데 FR-14/AC-15의 부하 검증 합격 기준은 "1분간 응답 지연이나 건너뛰기가 **한 번도** 없어야 함"입니다 — 외부 API 호출이 어느 정도 지연되는 건 흔한 일이라, 이 기준을 통과하려면 사실상 모든 응답이 2초 이내로 끝나야 하는 셈이라 처음 우려했던 2초 요건의 엄격함이 형태를 바꿔 다시 나타난 것에 가깝습니다. 타임아웃과 주기의 기본값 관계를 재검토하거나, "정상 응답인데 느려서 건너뜀"과 "오류로 인한 건너뜀"을 부하 검증 기준에서 구분하는 걸 권합니다.

2. **고정 스케줄의 기준 시각("시작 시각")이 장 마감/재개를 어떻게 다루는지 불명확합니다.** FR-12는 "장 마감·휴장 상태에서는 주기 조회를 중지"한다고 했는데, 재개 시 스케줄 원점(`시작 시각`)이 앱 최초 기동 시점을 계속 쓰는지, 아니면 각 재개 시점마다 새로 잡는지가 안 적혀 있습니다. 수학적으로는 어느 쪽이든 동작은 하지만, 구현 시 혼선을 피하려면 명시하는 게 좋겠습니다.
