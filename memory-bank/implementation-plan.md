# Stock2 구현 계획

| 항목        | 값                                                                 |
| ----------- | ------------------------------------------------------------------ |
| 기준 문서   | `product-design-document.md` v0.2.9                                |
| 개발 규칙   | 저장소 루트 `AGENTS.md`                                            |
| 디자인 기준 | `design_sample/*.png` 5개 화면                                     |
| 목표        | 로컬 환경에서 PDD의 MVP 기능과 수용 조건을 검증 가능한 상태로 완성 |
| 아키텍처    | Next.js 기반 모듈형 모놀리스                                       |
| 문서 상태   | Initial implementation plan                                        |
| 작성일      | 2026-09-16                                                         |

## 1. 계획의 원칙

- 제품 동작, 계산식, 상태와 기능 범위는 PDD를 단일 기준으로 삼는다.
- `design_sample/*.png`는 시각적 기준으로만 사용한다. 샘플에 보이는 뉴스/AI 분석, 간단 수익률
  계산기 등 MVP 외 기능은 구현하지 않는다.
- 샘플과 PDD가 충돌하면 PDD를 우선한다. 특히 포트폴리오 분석은 `백테스트`가 아니라
  `현재 보유 수량 기준 과거 추정 가치`로 표현하며 상장 전 기간을 0원으로 계산하지 않는다.
- 화면부터 임시 데이터로 크게 만든 뒤 로직을 끼워 넣지 않는다. 설정·도메인·계약·공급원 경계를 먼저
  만들고, 사용자 흐름별로 UI까지 완성하는 수직 단위로 진행한다.
- 각 단계는 구현, 자동 테스트, 문서 갱신과 검증 결과 기록까지 끝나야 완료로 본다.
- 공급원 제약이 확인되지 않은 기능은 임의 값으로 구현하지 않는다. 검증 결과를 PDD 또는 ADR에 기록한
  뒤 지원 범위를 확정한다.

## 2. 목표 아키텍처와 데이터 흐름

```text
Browser UI
  -> Next.js route handler / server boundary
    -> application use case
      -> domain policy and calculation
      -> provider/repository/clock port
        -> Yahoo Finance adapter
        -> SQLite repository
        -> fixed-tick polling scheduler
```

주요 경계는 다음과 같다.

- UI는 공급원과 DB를 직접 알지 못하고 서버 계약 DTO만 사용한다.
- 도메인 계산은 시간·네트워크·React·DB에 의존하지 않는 순수 함수로 유지한다.
- Yahoo Finance 응답, 환경 변수, API 요청, localStorage 데이터는 각각의 신뢰 경계에서 검증한다.
- 최신 수집 결과와 마지막 정상 스냅샷을 분리한다.
- 자동 조회의 네 그룹은 동일 스케줄 원점을 공유하되 실행 상태와 실패 카운터는 독립적으로 관리한다.
- 브라우저 로컬 저장소에는 관심 종목과 포트폴리오만 저장한다. OHLCV와 수집 스냅샷은 서버 저장소가
  담당한다.

## 3. 전체 단계와 의존 관계

```text
M0 공급원·기술 검증
  -> M1 프로젝트 기반과 품질 도구
    -> M2 도메인·계약·설정
      -> M3 저장소·공급원 어댑터
        -> M4 고정 시각 수집 엔진
          -> M5 시황·검색·종목 상세
            -> M6 관심 종목·포트폴리오
              -> M7 과거 추정 가치·추천 백테스트
                -> M8 신뢰성·접근성·디자인 완성
                  -> M9 부하·안정성·MVP 수용 검증
```

M2 이후 일부 UI 뼈대와 도메인 작업은 병행할 수 있지만, 실제 공급원 연동 화면은 M3 계약이 확정된 뒤
진행한다. M9 통과 전에는 MVP 완료로 표시하지 않는다.

### 8.1 스케줄러

- [x] `Clock`, scheduler와 provider를 포트로 주입한다.
- [x] `T0 + interval × n` 방식으로 다음 고정 조회 시각을 계산한다.
- [x] 주요 지수, 인기 종목, 관심 종목과 포트폴리오 종목을 독립 작업으로 만든다.
- [x] 같은 그룹의 이전 요청이 실행 중이면 해당 회차만 건너뛰고 횟수를 기록한다.
- [x] 빈 관심 종목/포트폴리오 그룹은 외부 호출 없이 `empty`로 처리한다.
- [x] 적용 배치 크기로 심볼을 나누고 일부 배치 실패 시 성공 결과를 유지한다.
- [x] 그룹별 시작/완료 시각, 응답 시간, batch 결과와 건너뛰기를 구조화 로그로 기록한다.

### 8.2 실패와 복구

- [x] 최초 실패 후 다음 고정 시각부터 최대 세 번 재요청한다.
- [x] 성공하면 해당 그룹의 실패 횟수와 delayed 상태를 초기화한다.
- [x] 세 번째 재요청 실패 확정 시 해당 그룹만 중단한다.
- [x] 그룹별 다시 시도는 해당 그룹만 초기화하고 다음 고정 시각에 재개한다.
- [x] 일반 조회 실패/타임아웃은 자동 조회 카운터를 변경하지 않는다.
- [x] 장 마감·휴장에는 자동 조회를 중지한다.
- [x] 장중 전환 감지 시각을 새 T0로 사용하고 중지 기간 회차를 소급하지 않는다.
- [x] 장 재개만으로 기존 실패 카운터나 중단 상태를 초기화하지 않는다.

### 8.3 결정론적 테스트

- [x] 부분 성공, 성공 후 복구, 그룹별 다시 시도와 전체 초기화를 검증한다.
- [x] 일반 조회와 자동 조회 카운터의 독립성을 검증한다.
- [x] 장 재개 원점 재설정을 검증한다.
