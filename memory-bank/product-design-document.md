## 1. 제품 개요

### 1.1 목적

한국어를 사용하는 개인 투자자가 국내외 시장 현황, 종목별 현재·과거 가격, 관심 종목 및 포트폴리오의 과거 가치 변화를 한곳에서 탐색할 수 있는 웹 대시보드를 제공한다.

Stock2는 데이터 탐색과 비교를 돕는 정보 도구다. 투자 판단을 대신하거나 수익을 보장하지 않으며, 매매 신호·자동 주문·계좌 연동은 제공하지 않는다.

### 1.2 해결할 문제

사용자는 활발하게 거래되는 종목을 찾고 장기 가격 흐름을 비교하기 위해 여러 화면과 데이터 소스를 오가야 한다. 포트폴리오를 분석할 때는 가격, 환율, 상장 시점이 다른 자산을 직접 정리해야 하며, 데이터 지연이나 누락이 정상 결과처럼 보이면 분석 결과를 신뢰하기 어렵다.

Stock2는 다음 방법으로 이 문제를 줄인다.

- 시장별 주요 지수와 거래량·등락률 기준 인기 종목을 한 화면에 제공한다.
- 종목별 OHLCV 과거 시계열을 기간별 차트로 제공한다.
- 관심 종목과 포트폴리오를 구성하고 현재 원화 평가금액을 계산한다.
- 현재 보유 수량 기준 과거 추정 가치와 추천 포트폴리오 백테스트를 구분해 제공한다.
- 데이터 기준 시각, 지연, 누락 및 분석 가정을 결과와 함께 표시한다.
- 마지막 정상 스냅샷을 보존해 일시적인 수집 실패 시에도 이전 데이터를 확인할 수 있게 한다.

### 1.3 제품 원칙

- **정확성 우선:** 갱신 속도보다 데이터 출처, 기준 시각과 계산 가정을 명확히 표시한다.
- **분석 유형 구분:** 과거 가격 조회, 현재 보유량의 과거 추정 가치, 전략 백테스트를 서로 다른 결과로 표현한다.
- **상태 투명성:** 로딩, 지연, 부분 누락, 실패 상태를 숨기지 않는다.
- **비파괴적 동작:** 저장 데이터는 명시적 확인 없이 삭제하거나 덮어쓰지 않는다.
- **정보 제공 한정:** 매매 권유, 자동 주문과 수익 보장 표현을 사용하지 않는다.

## 2. 대상 사용자와 핵심 시나리오

### 2.1 대상 사용자

- 한국어 UI로 국내외 시장을 모니터링하는 개인 투자자
- 종목의 단기·장기 가격 흐름을 비교하려는 사용자
- 자신의 보유 종목과 추천 포트폴리오의 과거 움직임을 탐색하려는 사용자

### 2.2 핵심 사용자 흐름

#### 흐름 A — 시장 탐색

1. 사용자가 시장 또는 주요 지수를 선택한다.
2. 시스템이 최신 데이터와 데이터 기준 시각을 표시한다.
3. 사용자가 인기·급등락·업종별 종목을 확인한다.
4. 사용자가 종목을 선택해 상세 화면으로 이동한다.

#### 흐름 B — 종목 과거 시계열 분석

1. 사용자가 종목명 또는 티커를 검색한다.
2. 사용자가 분석 기간과 차트 유형을 선택한다.
3. 시스템이 OHLCV 과거 시계열과 데이터 범위를 표시한다.
4. 사용자가 캔들 차트와 라인 차트를 전환하며 가격 흐름을 확인한다.
5. 사용자가 종목을 관심 종목 또는 포트폴리오에 추가한다.

#### 흐름 C — 사용자 포트폴리오 분석

1. 사용자가 포트폴리오에 종목을 추가하고 현재 보유 수량을 입력한다.
2. 시스템이 최신 가격과 환율을 사용해 원화 평가금액을 계산한다.
3. 사용자가 분석 기간을 선택한다.
4. 시스템이 현재 보유 수량 기준 과거 추정 가치와 데이터 가정을 표시한다.
5. 데이터가 부족한 종목이 있으면 분석 시작일 또는 제외 사유를 표시한다.

#### 흐름 D — 추천 포트폴리오 비교

1. 사용자가 추천 포트폴리오 목록을 확인한다.
2. 사용자가 자산 비중, 누적 수익률, 연환산 수익률, 변동성과 MDD를 비교한다.
3. 사용자가 분석 기간과 정렬 기준을 변경한다.
4. 사용자가 추천안을 새 포트폴리오로 복사한다.

## 3. 범위

### 3.1 MVP 포함

1. 주식 검색·시황, 포트폴리오 분석, 추천 포트폴리오 탭
2. KOSPI, KOSDAQ, NASDAQ, S&P 500 주요 지수 조회
3. 인기·급등락 종목과 업종별 시황
4. 티커 검색과 종목 상세 정보
5. OHLCV 과거 시계열 조회
6. 캔들 차트와 라인 차트 전환
7. 관심 종목 추가·삭제
8. 포트폴리오 종목·보유 수량 관리 및 현재 원화 평가금액
9. 현재 보유 수량 기준 과거 추정 가치 분석
10. 추천 포트폴리오 구성·비교·복사
11. 데이터 수집 상태와 마지막 정상 스냅샷 표시

### 3.2 MVP 제외

- 매매 신호와 개인화된 투자 추천
- 주문·증권 계좌 연동
- 실제 매매 내역 기반 수익률 계산
- 세금 최적화 및 세금 신고
- 푸시·이메일 알림
- 사용자 계정과 여러 기기 간 동기화
- 외부 공개 배포 및 상용 서비스 운영

### 3.3 후속 버전

- 실시간 뉴스와 AI 분석
- 배당·매매·입출금 내역을 반영한 실제 포트폴리오 성과 분석
- 사용자별 여러 포트폴리오 저장
- 목표 비중과 리밸런싱 시뮬레이션
- 데이터 공급원 다중화
- 서버·로컬 캐싱 계층과 데이터 유형별 TTL 정책
- 요청 병합, 캐시 무효화 및 분산 캐시 도입 검토
- 서버 시스템과 클라이언트 시스템 분리
- 서버 데이터 수집 주기와 클라이언트 UI 동기화 주기의 독립 설정

## 4. 용어와 분석 유형

### 4.1 종목 과거 시계열

특정 종목의 과거 OHLCV 데이터를 의미한다. 사용자의 실제 투자 성과와 무관한 시장 데이터다.

### 4.2 현재 보유 수량 기준 과거 추정 가치

사용자가 현재 입력한 보유 수량에 과거 종가와 당시 환율을 적용해 계산한 추정치다. 매수일, 매입가, 입출금과 실제 보유 수량 변화를 반영하지 않으므로 `실제 투자 수익률` 또는 `백테스트 수익률`로 표현하지 않는다.

### 4.3 추천 포트폴리오 백테스트

초기 투자금과 목표 비중을 정해 과거 데이터에 적용한 가상 시뮬레이션이다. 수익률·MDD와 함께 분석 기간, 배당, 환율, 리밸런싱, 수수료와 세금 가정을 표시한다.

## 6. 기능 요구사항

### FR-01 주요 지수와 시장 현황

- KOSPI, KOSDAQ, NASDAQ, S&P 500 지수의 최신 값과 전일 대비 등락률을 표시한다.
- 주요 지수 그룹은 KOSPI, KOSDAQ, NASDAQ, S&P 500의 네 지수로 고정한다.
- 지수마다 시장 상태, 시장 데이터 기준 시각과 수집 완료 시각을 표시한다.
- 사용자는 1시간, 1일, 1주, 1개월, 6개월, 1년, 3년, 5년 범위를 선택할 수 있다.
- 주요 지수 차트의 최대 조회 기간은 5년이다. 주요 지수에는 7년과 10년 옵션을 제공하지 않는다.
- 기본 기간은 5년으로 한다.
- 선택한 기간에 사용할 수 없는 데이터 간격은 비활성화하고 이유를 표시한다.

### FR-02 종목 검색과 상세 정보

- 종목명과 티커를 대상으로 검색한다.
- 같은 티커가 여러 거래소에 존재할 수 있으므로 거래소와 통화를 함께 표시한다.
- 검색 결과에는 종목명, 티커, 거래소, 통화, 현재가와 전일 대비 등락률을 표시한다.
- 잘못된 티커, 지원하지 않는 거래소와 검색 결과 없음 상태를 구분한다.

### FR-03 인기·급등락 및 업종별 시황

- 인기 종목의 산정 기준을 화면에 표시한다.
- 상승률 상위와 하락률 상위 종목을 분리한다.
- 업종별 등락률과 구성 종목 수를 표시한다.
- 가격 상승과 하락은 색상뿐 아니라 부호와 텍스트로도 구분한다.

### FR-04 과거 시계열 수집

- 시계열 데이터는 OHLCV 형태로 저장한다.
- 필수 필드는 `symbol`, `exchange`, `interval`, `timestamp`, `open`, `high`, `low`, `close`, `adjusted_close`, `volume`, `currency`, `source`다.
- 시계열 레코드는 `symbol + exchange + interval + timestamp + source`의 조합으로 식별한다.
- `interval`은 `1m`, `5m`, `15m`, `1h`, `1d`처럼 공급원 값과 내부 표준값의 매핑이 명확한 코드로 저장한다.
- 내부 시각은 UTC로 저장하며 UI에는 거래소 현지 시각과 한국 표준시를 구분해 표시한다.
- 중복 타임스탬프, 음수 거래량, 고가·저가 관계 오류와 필수 필드 누락을 검증한다.
- 데이터 공백이 있으면 보간해 정상 데이터처럼 만들지 않고 누락 구간을 표시한다.
- 액면분할과 배당을 반영하는 조정 종가의 사용 여부를 화면에 표시한다.

### FR-05 기간과 데이터 간격

- 이 절의 기간 정책은 개별 종목 차트와 포트폴리오 분석에 적용한다.
- 개별 종목 차트와 포트폴리오 분석의 지원 기간은 1시간, 1일, 1주, 1개월, 6개월, 1년, 3년, 5년, 7년, 10년이며 최대 조회 기간은 10년이다.
- 짧은 기간에는 분·시간 단위 데이터를, 장기 기간에는 일 단위 데이터를 사용한다.
- 실제 기간·간격 조합은 데이터 공급원이 제공하는 범위 안에서 활성화한다.
- 요청 기간보다 데이터가 짧으면 실제 제공 시작일과 부족한 이유를 표시한다.

### FR-06 종목 차트

- 기본 차트는 캔들 차트로 한다.
- 사용자는 라인 차트로 전환할 수 있다.
- 캔들 차트는 시가, 고가, 저가, 종가와 거래량을 사용한다.
- 라인 차트는 조정 종가를 기본값으로 사용한다.
- 차트에는 종목, 통화, 기간, 데이터 간격, 데이터 기준 시각을 표시한다.
- 로딩·빈 데이터·부분 누락·전체 실패 상태를 각각 제공한다.

### FR-07 관심 종목

- 사용자는 종목 상세 화면에서 관심 종목을 추가할 수 있다.
- 사용자는 관심 종목을 삭제할 수 있다.
- 동일 거래소·동일 종목의 중복 추가를 방지한다.
- MVP에서는 로컬 저장소에 보관한다.
- 최초 저장 시 브라우저 데이터 삭제, 애플리케이션 초기화 또는 기기 변경으로 데이터가 유실될 수 있음을 안내한다.
- 관심 종목 영역에 `이 기기에만 저장됨` 상태를 지속적으로 확인할 수 있게 표시한다.
- 관심 종목 최대 저장 수는 `limits.watchlist_max_symbols` 설정값을 적용하며 기본값은 `20`개다.
- 적용된 최대 저장 수를 초과해 추가하려고 하면 저장하지 않고 현재 최대 저장 수와 기존 종목 삭제 방법을 안내한다.

### FR-08 사용자 포트폴리오

- 사용자는 종목을 포트폴리오에 추가하고 삭제할 수 있다.
- 사용자는 0보다 큰 보유 수량을 입력할 수 있다.
- 최신 평가금액은 `보유 수량 × 최신 가격 × 최신 환율`로 계산한다.
- 각 가격과 환율의 기준 시각을 표시한다.
- 포트폴리오 전체 원화 평가금액과 종목별 비중을 표시한다.
- 입력 오류는 해당 필드 옆에서 설명하고 다른 종목의 정상 계산을 막지 않는다.
- 포트폴리오는 MVP에서 로컬 저장소에만 저장한다.
- 최초 저장과 전체 삭제 전에 로컬 저장 범위와 복구 불가 가능성을 안내한다.
- 포트폴리오 최대 구성 종목 수는 `limits.portfolio_max_symbols` 설정값을 적용하며 기본값은 `10`개다.
- 적용된 최대 구성 수를 초과해 추가하려고 하면 저장하지 않고 현재 최대 구성 수와 기존 종목 삭제 방법을 안내한다.

### FR-09 사용자 포트폴리오 과거 추정 가치

- 기본 분석 기간은 5년으로 한다.
- 사용자는 6개월, 1년, 3년, 5년, 7년, 10년을 선택할 수 있다.
- 일별 추정 가치는 `현재 보유 수량 × 해당 일자의 조정 종가 × 해당 일자의 환율`을 종목별로 계산한 뒤 합산한다.
- 종목이 상장되기 전 기간을 0원으로 계산하지 않는다.
- 기본 분석 시작일은 모든 포함 종목과 환율 데이터가 존재하는 최초 공통 날짜로 한다.
- 특정 종목 때문에 공통 분석 기간이 요청 기간보다 짧아지면 분석 전에 영향받는 종목과 실제 시작일을 표시한다.
- 사용자는 `모든 종목을 유지하고 공통 기간으로 분석`, `데이터가 짧은 종목을 제외하고 요청 기간 유지`, `분석 취소` 중 하나를 선택할 수 있어야 한다.
- 제외 옵션을 선택하면 제외될 종목, 제외 사유, 제외 전후 분석 기간을 미리 보여준다.
- 제외된 종목은 포트폴리오에서 삭제하지 않고 해당 분석 실행에서만 제외한다.
- 결과 제목과 설명에 `현재 보유 수량 기준 과거 추정 가치`를 명시한다.
- 실제 매입가와 현금 흐름이 없으면 실제 투자 수익률을 표시하지 않는다.

### FR-10 추천 포트폴리오 백테스트

- 기본 초기 투자금은 1,000만 원으로 한다.
- 구성 비율의 합은 100%여야 한다.
- 소수점 단위 매수는 시뮬레이션에서 허용하되 가정으로 표시한다.
- 기본 분석 기간은 10년으로 하고 사용자는 6개월, 1년, 3년, 5년, 7년, 10년을 선택할 수 있다.
- 모든 구성 자산의 데이터가 존재하는 최초 공통 날짜를 시작일로 사용한다.
- 상장 전 기간은 0원으로 계산하지 않는다.
- 기본값은 조정 종가 사용, 배당 재투자 포함, 월별 리밸런싱, 수수료·세금 0원으로 한다.
- 모든 가정은 결과 옆에서 확인할 수 있어야 한다.
- 누적 수익률, CAGR, 연환산 변동성과 MDD를 표시한다.
- 포트폴리오 비중을 원형 차트와 표로 함께 표시한다.

### FR-11 추천 포트폴리오 복사

- 추천안을 선택하면 `새 포트폴리오로 저장`을 기본 동작으로 한다.
- 기존 포트폴리오 덮어쓰기는 변경 전후 미리보기와 별도 확인을 거친다.
- 취소하면 기존 포트폴리오를 변경하지 않는다.
- 기본 정렬은 MDD가 낮은 순으로 하며 수익률, 변동성, 구성 종목 수 정렬을 제공한다.

초기 예시는 다음과 같다. 티커와 비율은 구현 전에 데이터 공급원에서 다시 검증한다.

| 포트폴리오         | 구성                                          |
| ------------------ | --------------------------------------------- |
| Stock 80 / Bond 20 | VTI 80%, BND 20%                              |
| Momentum 60 / 40   | MTUM 60%, BND 40%                             |
| All Weather        | VTI 30%, TLT 40%, IEF 15%, DBC 7.5%, GLD 7.5% |
| Golden Butterfly   | IJS 20%, VTI 20%, SHY 20%, TLT 20%, GLD 20%   |

이 문서에서 All Weather 원자재 자산 티커는 `DBC`로 정의한다. 구현 시 데이터 공급원 심볼 매핑만 검증하며 `BC`로 대체하지 않는다.

### FR-12 데이터 갱신과 상태

- 장중 주요 지수와 현재가 데이터의 조회 주기는 설정 키 `realtime.poll_interval_seconds`로 관리한다.
- `realtime.poll_interval_seconds`의 기본값은 `2`초다.
- 설정 검증과 폴백을 거쳐 실제 자동 주기 조회에 사용하는 `realtime.poll_interval_seconds` 값을 이 문서에서 `적용 자동 조회 주기`라고 한다.
- 조회 주기는 코드에 하드코딩하지 않으며 운영자가 설정 파일 또는 환경 변수로 늘릴 수 있어야 한다.
- 설정 가능한 값은 2초 이상의 정수로 제한한다.
- 설정값이 없거나 숫자가 아니거나 정수가 아니면 기본값 2초를 적용한다.
- 2보다 작은 정수가 입력되면 최솟값 2초를 적용한다.
- 폴백 또는 최솟값 보정이 발생하면 입력값, 적용값 2초와 보정 사유를 개발 로그에 기록한다.
- 설정값은 실제 데이터 조회 요청의 고정된 목표 시작 간격이며 단순 화면 재렌더링 주기가 아니다.
- 조회 스케줄은 애플리케이션의 데이터 수집 시작 시각을 기준으로 `시작 시각 + (조회 주기 × n)`에 도래하는 고정 시각 방식으로 계산한다.
- `자동 주기 조회`는 고정 조회 시각마다 실행하는 주요 지수, 인기 종목, 관심 종목과 포트폴리오 종목의 네 그룹 조회를 의미한다.
- `일반 조회`는 검색, 종목 상세·과거 시계열 조회 등 사용자의 명시적 동작으로 한 번 실행되는 비주기성 조회를 의미한다.
- 실행 중인 조회 주기는 화면의 데이터 상태 영역에 표시한다.
- 설정 변경은 애플리케이션 재시작 후 적용하는 것을 MVP 기준으로 한다.
- 각 고정 조회 시각에 해당 그룹의 이전 요청이 실행 중이면 중복 요청을 만들지 않고 해당 그룹의 회차를 건너뛰며 건너뛰기 횟수를 기록한다.
- 외부 데이터 요청 타임아웃은 `provider.request_timeout_seconds` 설정값을 적용하며 기본값은 `5`초다.
- 요청 시작 후 적용된 타임아웃 안에 응답을 받지 못하면 해당 요청을 종료하고 데이터 그룹을 `응답 지연` 상태로 표시한다.
- `응답 지연` 상태에는 마지막 정상 갱신 시각, 현재 적용 중인 조회 주기와 요청 타임아웃을 함께 표시한다.
- 타임아웃된 요청은 같은 회차에서 즉시 재시도하지 않는다. 타임아웃 확정 시각보다 늦게 처음 도래하는 고정 조회 시각에 해당 그룹을 다시 요청한다.
- 타임아웃이 조회 주기보다 길면 요청 실행 중에 도래한 하나 이상의 조회 회차를 건너뛸 수 있으며, 요청 종료 후 스케줄을 현재 시각 기준으로 재정렬하지 않는다.
- 일반 조회에도 설정된 요청 타임아웃을 적용한다. 일반 조회의 요청 실패와 타임아웃은 사용자에게 단건 실패로 표시하되 자동 주기 조회의 재시도 횟수에는 포함하지 않으며, 세 번의 자동 재시도나 그룹 중단을 실행하지 않는다.
- 자동 주기 조회의 최초 타임아웃 또는 요청 실패 이후의 재시도 횟수만 데이터 그룹별로 관리한다.
- 다음 고정 조회 시각의 재요청이 성공하면 재시도 횟수를 0으로 초기화하고 `응답 지연` 상태를 해제한다.
- 최초 실패 이후 세 번의 재요청이 모두 실패하면 해당 데이터 그룹을 `실패` 상태로 전환하고 자동 조회를 중단한다.
- 그룹 중단 시점은 고정된 경과 시간이 아니라 세 번째 재요청의 실패 또는 타임아웃이 확정된 시점으로 한다.
- `적용 자동 조회 주기=2초`, 타임아웃 5초에서 모든 요청이 타임아웃되는 경우, 최초 요청과 세 번의 재요청은 수집 시작 후 0초, 6초, 12초, 18초에 시작하고 23초에 그룹을 `실패`로 전환한다.
- 한 데이터 그룹의 자동 조회 중단은 다른 그룹의 조회에 영향을 주지 않는다.
- `실패` 상태에는 해당 그룹만 복구하는 `다시 시도` 버튼을 제공한다.
- 사용자가 `다시 시도`를 실행하면 해당 그룹의 실패 횟수와 중단 상태만 초기화하고, 다른 그룹과 현재 화면 상태를 유지한 채 다음 고정 조회 시각에 자동 조회를 재개한다.
- 브라우저 새로고침은 모든 그룹의 실패 횟수와 중단 상태를 초기화하는 전체 복구용 보조 수단으로 제공한다.
- 각 응답에는 데이터 공급원의 기준 시각과 시스템 수집 완료 시각을 함께 표시한다.
- 데이터 공급원의 값이 이전 조회와 같더라도 정상 응답이면 조회 성공으로 처리하되 마지막 변동 시각을 별도로 표시한다.
- 공급원이 현재 `적용 자동 조회 주기`를 충족하지 못하면 운영자가 검증 결과에 따라 `realtime.poll_interval_seconds`를 명시적으로 늘리거나 공급원을 교체한다.
- 조회 주기 변경 사실은 설정 변경 기록에 남기며 애플리케이션이 임의로 주기를 변경하지 않는다.
- 장 마감·휴장 상태에서는 자동 주기 조회를 중지하고 시장 상태와 마지막 거래 시각을 표시한다.
- 시장 상태가 장 마감·휴장에서 장중으로 전환되면 시스템이 장중 전환을 감지한 시각을 새로운 데이터 수집 시작 시각으로 설정하고 고정 조회 스케줄의 원점을 다시 계산한다.
- 장 마감·휴장 동안 지나간 조회 회차는 소급 실행하지 않으며, 장 재개 시 새로운 원점에서 첫 자동 주기 조회를 시작한다.
- 장 재개에 따른 스케줄 원점 재설정은 기존 그룹의 실패 횟수와 중단 상태를 자동으로 초기화하지 않는다.
- 사용자는 데이터 그룹별 `다시 시도`를 실행할 수 있으며, 이는 브라우저 전체 새로고침과 구분한다.
- 상태는 `로딩`, `정상`, `부분 성공`, `응답 지연`, `오래된 데이터`, `실패`로 구분한다.
- 새 수집이 실패하면 오류 원인과 재시도 방법을 표시한다.
- 마지막 정상 스냅샷이 있으면 이전 데이터임을 명확히 표시한 뒤 조회할 수 있게 한다.
- 캐시 계층은 MVP에서 구현하지 않으며 후속 과제로 분리한다.

### FR-13 서버·클라이언트 주기 동기화

- MVP의 서버 데이터 조회와 클라이언트 UI 갱신은 동일한 `realtime.poll_interval_seconds` 값을 사용한다.
- 서버가 적용 중인 조회 주기를 클라이언트에 전달하며 클라이언트는 별도의 주기를 하드코딩하지 않는다.
- 클라이언트는 서버에서 받은 적용값을 화면에 표시하고 동일한 간격으로 서버의 최신 상태를 읽는다.
- 서버 조회가 진행 중이거나 새 데이터가 없으면 클라이언트는 마지막 정상 화면을 유지한다.
- 클라이언트 갱신이 서버의 외부 데이터 공급원 호출을 직접 발생시키지 않도록 데이터 조회 책임은 서버에 둔다.

### FR-14 데이터 그룹별 독립 호출

- 실시간 조회는 `주요 지수`, `인기 종목`, `관심 종목`, `포트폴리오 종목`의 네 데이터 그룹으로 분리한다.
- `주요 지수` 그룹은 KOSPI, KOSDAQ, NASDAQ, S&P 500의 네 지수를 각각 조회 대상으로 포함한다.
- 각 조회 주기마다 네 그룹을 각각 별도의 서버 측 호출 작업으로 실행한다.
- 공급원 1회 요청당 최대 심볼 수는 `provider.max_symbols_per_request` 설정값을 적용하며 기본값은 `10`개다.
- 한도 초과 시 요청 분할 크기는 `provider.batch_size` 설정값을 적용하며 기본값은 `10`개다.
- 한 그룹의 조회 대상이 적용된 분할 크기를 초과하면 해당 크기의 배치로 나누어 요청한다.
- 주요 지수 그룹은 기본 설정에서 4개 지수를 하나의 배치로 요청하며, 적용된 분할 크기가 4보다 작으면 같은 규칙으로 나눈다.
- 기본 설정에서는 관심 종목 그룹을 최대 20개, 10개 단위의 최대 2개 배치로 요청한다.
- 기본 설정에서는 포트폴리오 종목 그룹을 최대 10개, 10개 단위의 최대 1개 배치로 요청한다.
- 인기 종목 그룹도 조회 대상이 적용된 분할 크기를 초과하면 동일한 기준으로 분할한다.
- 그룹별로 `로딩`, `정상`, `부분 성공`, `응답 지연`, `오래된 데이터`, `실패` 상태와 데이터 기준 시각을 독립적으로 관리한다.
- 분할 요청 중 일부 배치만 실패하면 성공한 배치 결과는 유지하고 해당 그룹을 `부분 성공`으로 표시한다.
- `부분 성공` UI에는 성공한 심볼 수, 실패한 심볼 수 또는 배치 수와 마지막 정상 갱신 시각을 표시한다.
- 한 그룹의 실패가 다른 그룹의 정상 결과를 숨기거나 실패 상태로 변경해서는 안 된다.
- 이전 요청이 끝나지 않은 그룹은 해당 그룹의 회차만 건너뛰고 다른 그룹의 조회는 계속한다.
- 관심 종목 또는 포트폴리오가 비어 있으면 해당 그룹의 외부 호출을 실행하지 않고 `데이터 없음` 상태로 처리한다.
- `적용 자동 조회 주기`로 네 그룹을 1분간 연속 조회하는 부하 검증에서 응답 지연이나 회차 건너뛰기가 한 번도 발생하지 않아야 합격으로 판정한다.
- 부하 검증 중 각 그룹의 요청 시작·완료 시각, 응답 시간과 건너뛰기 여부를 기록한다.

### FR-15 한도·배치·타임아웃 설정

- 다음 다섯 값은 코드에 하드코딩하지 않고 설정 파일 또는 환경 변수로 관리한다.

| 설정 키                            | 의미                           | 기본값 |
| ---------------------------------- | ------------------------------ | -----: |
| `limits.watchlist_max_symbols`     | 관심 종목 최대 저장 수         |     20 |
| `limits.portfolio_max_symbols`     | 포트폴리오 최대 구성 종목 수   |     10 |
| `provider.max_symbols_per_request` | 공급원 1회 요청당 최대 심볼 수 |     10 |
| `provider.batch_size`              | 한도 초과 시 요청 분할 크기    |     10 |
| `provider.request_timeout_seconds` | 외부 데이터 요청 타임아웃(초)  |      5 |

- 다섯 설정값은 모두 1 이상의 정수만 허용한다.
- 설정값이 없거나 숫자가 아니거나 정수가 아니거나 1보다 작으면 해당 키의 기본값을 적용한다.
- `provider.batch_size`가 `provider.max_symbols_per_request`보다 크면 분할 크기를 적용된 1회 요청 최대 심볼 수로 보정한다.
- 그룹별 배치 수는 `ceil(조회 대상 심볼 수 ÷ 적용된 분할 크기)`로 계산한다.
- 폴백 또는 보정이 발생하면 설정 키, 입력값, 적용값과 사유를 개발 로그에 기록한다.
- 서버는 검증을 마친 적용값을 클라이언트에 전달하고, 클라이언트는 관심 종목·포트폴리오 추가 제한, 안내 문구와 응답 지연 상태의 타임아웃 표시에 해당 값을 사용한다.
- 설정 변경은 애플리케이션 재시작 후 적용하는 것을 MVP 기준으로 하며, 기존 저장 데이터가 새 한도를 초과하더라도 자동 삭제하지 않는다.
- 기존 저장 데이터가 변경된 한도를 초과하면 기존 항목의 조회와 삭제는 허용하되 신규 추가를 차단하고 현재 저장 수와 적용된 한도를 표시한다.

### FR-16 부분 화면 갱신

- 데이터 조회는 설정된 주기마다 수행하되 화면 전체를 매 주기마다 다시 렌더링하지 않는다.
- 값 또는 상태가 변경된 지수, 현재가, 상태 배지와 관련 차트 데이터만 부분 갱신한다.
- 변경되지 않은 표, 차트와 입력 컴포넌트는 재생성하지 않는다.
- 부분 갱신 중 사용자의 스크롤 위치, 키보드 포커스, 검색어, 필터, 선택 탭과 입력 중인 보유 수량을 유지한다.
- 화면 전체 렌더링은 최초 진입, 사용자의 명시적인 화면 전환 또는 전체 구조 변경이 필요한 경우에만 수행한다.
- 부분 갱신 실패 시 기존 화면을 유지하고 해당 데이터 그룹에만 오류 상태를 표시한다.

## 7. 계산 정의

### 7.1 일별 수익률

`일별 수익률 = 당일 포트폴리오 가치 / 전일 포트폴리오 가치 - 1`

### 7.2 누적 수익률

`누적 수익률 = 종료 가치 / 시작 가치 - 1`

### 7.3 CAGR

`CAGR = (종료 가치 / 시작 가치)^(365 / 분석 일수) - 1`

분석 기간이 1년 미만이면 CAGR 대신 누적 수익률을 우선 표시한다.

### 7.4 연환산 변동성

일별 수익률의 표준편차에 `√252`를 곱한다. 다른 기준을 사용할 경우 결과에 표시한다.

### 7.5 MDD

각 날짜의 누적 최고 가치 대비 하락률 중 최솟값의 절댓값을 사용한다. MDD 값과 함께 해당 고점일·저점일을 표시한다.

### 7.6 환율

- 외화 자산은 각 거래일의 종가 기준 환율을 사용한다.
- 휴장일 또는 환율 누락일은 미래 값을 사용하지 않고 가장 최근의 이전 유효 환율을 적용한다.
- 날짜 `t`의 환율이 없을 때는 `FX(t) = FX(s)`를 사용하며, `s`는 `s ≤ t`를 만족하는 가장 최근 유효 환율 날짜다.
- 한국과 미국의 거래일이 다르면 종목 가격 날짜를 기준으로 환율 시계열을 정렬한 뒤 이전 유효값 채우기를 적용한다.
- 이전 유효값을 적용한 날짜와 원래 환율 기준일을 분석 결과에 기록한다.
- 최신 평가금액에는 최신 이용 가능한 환율과 그 기준 시각을 표시한다.

## 8. 데이터 공급원과 계약

### 8.1 공급원

- 초기 데이터 공급원은 Yahoo Finance 연동 어댑터로 한다.
- UI와 분석 로직은 공급원 구현과 분리한다.
- 개발 전에 시장별 데이터 범위, 과거 기간·간격, 호출 제한, 데이터 지연과 이용 조건을 검증한다.
- 지원되지 않는 기능은 임의의 값으로 대체하지 않고 비활성화 사유를 표시한다.
- 브라우저가 Yahoo Finance를 직접 호출하지 않으며 모든 외부 데이터 요청은 애플리케이션의 서버 측 어댑터를 통한다.
- 초기 공급원은 현재 `적용 자동 조회 주기`를 기준으로 검증한다.
- 공급원이 `적용 자동 조회 주기`를 충족하지 못하면 운영자가 검증 결과에 따라 `realtime.poll_interval_seconds`를 늘리거나 공급원을 교체하고 변경 사유와 측정 결과를 기록한다.
- 설정을 변경한 경우 재시작 후 새 값을 `적용 자동 조회 주기`로 확정하고 동일한 1분 부하·스모크 테스트를 다시 실행해 합격 여부를 판정한다.

### 8.2 종목 식별

- 종목은 티커만이 아니라 거래소와 함께 식별한다.
- 통화는 ISO 4217 코드를 사용한다.
- 동일 자산의 심볼이 공급원마다 다르면 매핑 테이블을 사용한다.

### 8.3 시각과 시장 상태

- 내부 시각은 UTC로 저장한다.
- `market_timestamp`와 `collected_at`을 구분한다.
- 장 마감·휴장 시 마지막 거래 시각과 시장 상태를 표시하고 오류로 취급하지 않는다.
- 데이터 신선도 기준을 넘으면 `오래된 데이터`로 표시한다.

### 8.4 스냅샷

- 최신 데이터와 마지막 정상 스냅샷을 구분해 저장한다.
- 검증이 완료된 뒤에만 마지막 정상 스냅샷을 교체한다.
- 실패 결과를 정상 스냅샷에 합쳐 완전한 데이터처럼 표시하지 않는다.

### 8.5 후속 과제 — 캐시 전략

- MVP의 실시간 주기 조회 경로에는 캐시를 적용하지 않는다.
- 캐시 전략은 실제 호출량, 응답 시간과 공급원 제한을 측정한 뒤 후속 버전에서 설계한다.
- 후속 설계 범위에는 데이터 유형별 TTL, 요청 병합, 수동 무효화, 로컬·서버·분산 캐시 선택과 장애 시 폴백이 포함된다.
- 캐시를 도입하더라도 화면에는 원본 데이터 기준 시각과 캐시 저장 시각을 구분해 표시한다.

### 8.6 후속 과제 — 서버·클라이언트 분리

- 서버와 클라이언트가 분리되는 버전에서는 서버가 클라이언트 접속 여부와 무관하게 설정된 주기로 외부 데이터 공급원과 계속 동기화한다.
- 서버 수집 주기는 `server.poll_interval_seconds`로 관리하며 기본값은 현재 `realtime.poll_interval_seconds`를 승계한다.
- `server.poll_interval_seconds`는 2초 이상의 정수로 제한하고 기본값은 2초로 한다.
- 서버 주기 설정이 없거나 숫자가 아니거나 정수가 아니면 2초를 적용하며, 2보다 작은 정수도 최솟값 2초로 보정한다.
- 클라이언트는 외부 데이터 공급원을 직접 호출하지 않고 서버가 보관한 최신 데이터만 읽는다.
- 클라이언트 UI 동기화 주기는 `client.refresh_interval_seconds`로 관리하며 사용자가 UI에서 변경할 수 있게 한다.
- `client.refresh_interval_seconds`는 2초 이상의 정수로 제한하고 기본값은 2초로 한다.
- 클라이언트 주기 설정이 없거나 숫자가 아니거나 정수가 아니면 2초를 적용하며, 2보다 작은 정수도 최솟값 2초로 보정한다.
- 서버 또는 클라이언트 주기 보정이 발생하면 입력값, 적용값 2초와 보정 사유를 개발 로그에 기록한다.
- 클라이언트 주기 변경은 서버의 외부 데이터 수집 주기에 영향을 주지 않는다.
- 클라이언트는 서버 데이터 기준 시각, 서버 수집 완료 시각과 클라이언트 화면 반영 시각을 구분해 표시한다.
- 서버와 클라이언트의 연결이 끊기면 마지막 정상 화면을 유지하고 연결 끊김 상태와 마지막 성공 동기화 시각을 표시한다.

## 10. 접근성 및 반응형 요구사항

- 키보드만으로 검색, 기간 선택, 차트 전환, 관심 종목 추가, 수량 입력과 복사를 사용할 수 있어야 한다.
- 포커스 표시가 명확해야 한다.
- 입력 요소에 보이는 라벨과 오류 설명을 제공한다.
- 상승·하락과 상태는 색상뿐 아니라 부호·텍스트·아이콘으로 전달한다.
- 표 헤더와 정렬 상태를 보조 기술이 이해할 수 있게 제공한다.
- 차트의 핵심 데이터는 표 또는 텍스트 요약으로도 제공한다.
- 200% 확대에서도 핵심 기능이 가려지거나 겹치지 않아야 한다.
- 원형·캔들·라인 차트는 SVG 기반 또는 동등한 벡터 품질의 렌더링을 사용해 고해상도와 200% 확대에서 선과 텍스트가 깨지지 않아야 한다.
- 모바일에서는 표를 가로 스크롤할 수 있게 하고 차트·컨트롤의 최소 가독성을 유지한다.

## 11. 비기능 요구사항

### 11.1 성능

- 정상 네트워크와 데이터 공급원 정상 응답 기준 첫 화면을 5초 이내에 표시하는 것을 목표로 한다.
- 검색, 필터와 정렬은 1초 이내에 반영한다.
- 장기 시계열 분석은 진행 상태를 표시하고 동일 요청을 중복 실행하지 않는다.
- 장중 실시간 데이터 조회는 수집 시작 시각을 기준으로 `realtime.poll_interval_seconds`의 고정 시각마다 시작하며, 요청이 겹칠 때는 해당 그룹의 회차를 건너뛰고 병렬 중복 실행하지 않는다.
- 네 데이터 그룹의 호출은 서로 독립적으로 실행하며 한 그룹의 지연이 다른 그룹의 시작을 막지 않아야 한다.
- 주기 갱신 시 변경된 컴포넌트만 다시 렌더링하고 전체 화면 재렌더링으로 사용자 입력이나 탐색 상태를 초기화하지 않는다.
- `적용 자동 조회 주기`로 네 그룹을 1분간 연속 호출했을 때 응답 지연과 회차 건너뛰기가 발생하지 않아야 한다.

### 11.2 신뢰성

- 일부 종목 또는 날짜의 오류가 전체 화면 장애로 이어지지 않게 한다.
- 분석 결과에는 사용한 데이터 범위와 제외된 종목을 기록한다.
- 같은 데이터와 가정으로 동일한 결과를 재현할 수 있어야 한다.
- 필수 스모크 테스트는 `적용 자동 조회 주기`로 1분간 실행하며 응답 지연과 회차 건너뛰기가 모두 0회여야 한다.
- 안정성 테스트는 최소 1시간 또는 한 시장 세션 동안 실행한다.
- 안정성 테스트 중 프로세스 메모리 사용량, 그룹별 오류율, HTTP 429 발생 횟수와 연결 재수립 횟수를 측정하고 결과를 기록한다.
- 안정성 테스트 중 처리되지 않은 예외로 애플리케이션이 종료되어서는 안 된다.

### 11.3 보안과 개인정보

- MVP는 로그인과 개인정보 수집을 포함하지 않는다.
- API 키는 소스 코드와 로그에 기록하지 않는다.
- 로컬 저장 포트폴리오의 초기화·삭제에는 확인 절차를 제공한다.

### 11.4 운영 범위

- MVP 완료 기준은 로컬 환경에서의 기능 검증이다.
- 외부 공개 배포, 운영 모니터링과 상용 SLA는 별도 범위로 다룬다.

## 12. 성공 기준과 수용 테스트

### 12.1 성공 기준

- 사용자가 시장 현황에서 종목 상세 차트까지 이동할 수 있다.
- 사용자가 지원 기간의 OHLCV 시계열을 캔들·라인 차트로 확인할 수 있다.
- 데이터 기간이 부족하거나 누락되면 원인과 실제 분석 범위가 표시된다.
- 사용자가 보유 수량을 입력하고 최신 원화 평가금액을 확인할 수 있다.
- 사용자가 현재 보유 수량 기준 과거 추정 가치와 그 한계를 확인할 수 있다.
- 사용자가 추천 포트폴리오의 수익률·변동성·MDD를 비교할 수 있다.
- 수집 실패 시 마지막 정상 스냅샷과 기준 시각을 확인할 수 있다.
- 기본 설정에서 장중 주요 지수와 현재가 데이터가 실제 공급원에 2초 간격으로 조회된다.
- 운영자가 설정값을 늘리면 변경된 주기가 재시작 후 실제 조회에 적용된다.
- 서버 조회와 클라이언트 UI 갱신이 동일한 적용 주기로 동작한다.
- 지수, 인기 종목, 관심 종목과 포트폴리오 종목의 조회 상태가 서로 독립적으로 표시된다.
- 주기 조회 중 화면 전체가 아닌 변경된 데이터 영역만 갱신된다.
- `적용 자동 조회 주기`의 1분 연속 부하 검증에서 모든 그룹이 응답 지연과 회차 건너뛰기 없이 동작한다.
- 응답 지연이 발생하면 영향받은 데이터 그룹과 마지막 정상 갱신 시각이 표시된다.
- 데이터가 짧은 종목 때문에 분석 기간이 축소될 때 사용자가 종목 유지·실행 제외·분석 취소 중 하나를 선택할 수 있다.
- 로컬 저장 데이터의 저장 범위와 유실 가능성을 사용자가 확인할 수 있다.
- 기본 설정에서 관심 종목 20개와 포트폴리오 종목 10개의 한도가 적용되며, 설정을 변경하면 재시작 후 변경된 한도가 적용된다.
- 기본 10개 또는 설정된 크기의 분할 요청에서 일부 배치가 실패하면 성공 데이터와 `부분 성공` 상태가 함께 표시된다.
- 설정된 타임아웃 후 처음 도래하는 고정 조회 시각에 재시도하고, 재시도 3회 실패 시 해당 그룹 조회가 중단된다.
- 중단된 그룹은 그룹별 `다시 시도`로 화면 상태와 다른 그룹을 유지한 채 복구할 수 있고, 브라우저 새로고침으로는 모든 그룹을 초기화할 수 있다.
- 일반 조회의 실패와 타임아웃은 자동 주기 조회의 재시도 횟수나 그룹 중단 상태에 영향을 주지 않는다.
- 장 마감·휴장 후 장중 전환을 감지하면 해당 시각을 새 스케줄 원점으로 사용하고 중지 기간의 회차를 소급 실행하지 않는다.
- 최소 1시간 또는 한 시장 세션 안정성 테스트의 측정 결과가 기록된다.

### 12.2 핵심 수용 테스트

#### AC-01 과거 시계열 정상 조회

- **Given** 선택 종목과 기간에 정상 OHLCV 데이터가 있고
- **When** 사용자가 기간을 선택하면
- **Then** 실제 데이터 시작·종료일, 간격과 기준 통화가 차트에 표시되어야 한다.

#### AC-02 시계열 부분 누락

- **Given** 요청 기간 중 일부 날짜의 데이터가 없고
- **When** 차트가 표시되면
- **Then** 누락 구간과 결과에 미치는 영향이 안내되어야 하며 임의 보간으로 정상 데이터처럼 보여서는 안 된다.

#### AC-03 상장 이력이 짧은 종목

- **Given** 종목의 상장일이 요청 시작일보다 늦고
- **When** 과거 분석을 실행하면
- **Then** 상장 전 기간을 0원으로 계산하지 않고 실제 데이터 시작일을 표시해야 한다.

#### AC-04 사용자 포트폴리오 과거 추정 가치

- **Given** 사용자가 두 개 이상의 종목과 보유 수량을 입력했고
- **When** 분석 기간을 선택하면
- **Then** 공통 데이터 시작일 이후의 일별 추정 가치와 적용 환율 기준이 표시되어야 한다.

#### AC-05 데이터가 짧은 종목 제외

- **Given** 한 종목의 상장 이력 때문에 요청한 분석 기간을 충족할 수 없고
- **When** 사용자가 해당 종목 제외 옵션을 선택하면
- **Then** 제외 종목과 제외 전후 분석 기간을 미리 보여준 뒤 해당 실행에서만 종목을 제외해야 하며 원래 포트폴리오는 변경되지 않아야 한다.

#### AC-06 추천 포트폴리오 백테스트

- **Given** 구성 비율의 합이 100%이고 모든 자산의 공통 데이터가 있으며
- **When** 백테스트를 실행하면
- **Then** 누적 수익률, CAGR, 변동성, MDD와 모든 계산 가정이 함께 표시되어야 한다.

#### AC-07 추천안 복사

- **Given** 기존 포트폴리오가 있고
- **When** 사용자가 추천안을 새 포트폴리오로 복사하면
- **Then** 기존 데이터는 유지되고 추천 구성이 별도로 저장되어야 한다.

#### AC-08 데이터 수집 실패

- **Given** 현재 수집이 실패했고 이전 정상 스냅샷이 있으며
- **When** 오류 상태가 표시되면
- **Then** 실패 원인, 재시도 방법과 이전 스냅샷의 기준 시각이 함께 보여야 한다.

#### AC-09 적용 자동 조회 주기의 실시간 조회

- **Given** 시장이 장중이고 데이터 공급원이 정상이며 `realtime.poll_interval_seconds=2`가 `적용 자동 조회 주기`로 확정되어 있고
- **When** 실시간 조회가 시작되면
- **Then** 시스템은 `적용 자동 조회 주기`인 2초 간격으로 새 조회를 시작하고 데이터 기준 시각과 수집 완료 시각을 각각 표시해야 한다.
- **And** 이전 요청이 진행 중이면 중복 요청을 시작하지 않고 건너뛴 회차를 진단 로그에 기록해야 한다.

#### AC-10 서로 다른 시장 휴장일의 환율 정렬

- **Given** 종목 가격은 존재하지만 같은 날짜의 환율 값이 없고 이전 유효 환율은 존재하며
- **When** 원화 환산 분석을 실행하면
- **Then** 미래 환율이 아닌 가장 최근 이전 유효 환율을 적용하고 적용 환율의 실제 기준일을 결과에 기록해야 한다.

#### AC-11 로컬 저장 안내

- **Given** 사용자가 관심 종목 또는 포트폴리오를 처음 저장하고
- **When** 저장을 확정하면
- **Then** 해당 데이터가 이 기기에만 저장되며 브라우저 데이터 삭제·초기화·기기 변경 시 유실될 수 있음을 안내해야 한다.

#### AC-12 조회 주기 설정 변경

- **Given** 운영자가 `realtime.poll_interval_seconds=5`로 설정하고 애플리케이션을 재시작했으며
- **When** 장중 실시간 조회가 시작되면
- **Then** 시스템은 코드 변경 없이 데이터 수집 시작 시각을 기준으로 5초마다 도래하는 고정 시각에 새 조회를 시작하고 화면에 현재 조회 주기 5초를 표시해야 한다.

#### AC-13 잘못된 조회 주기 설정의 기본값 적용

- **Given** `realtime.poll_interval_seconds`가 없거나 숫자가 아니거나 정수가 아니거나 2보다 작은 정수로 설정되어 있고
- **When** 애플리케이션이 시작되면
- **Then** 시스템은 조회 주기를 2초로 적용하고 입력값, 적용값과 보정 사유를 개발 로그에 기록해야 한다.
- **And** 화면에는 실제 적용된 조회 주기 2초를 표시해야 한다.

#### AC-14 서버·클라이언트 주기 동기화

- **Given** `realtime.poll_interval_seconds=5`로 설정되어 서버와 클라이언트가 시작되었고
- **When** 장중 데이터 동기화가 실행되면
- **Then** 서버는 5초 간격으로 외부 데이터를 조회하고 클라이언트는 서버가 전달한 동일 주기로 최신 상태를 읽어야 한다.
- **And** 클라이언트 코드에 별도의 고정 주기가 사용되어서는 안 된다.

#### AC-15 데이터 그룹별 독립 호출

- **Given** 주요 지수 그룹에 KOSPI, KOSDAQ, NASDAQ, S&P 500이 있고 인기 종목, 관심 종목과 포트폴리오 종목에도 조회 대상이 있으며 `적용 자동 조회 주기`가 확정되어 있고
- **When** `적용 자동 조회 주기`로 1분 동안 연속 부하 검증을 실행하면
- **Then** 네 데이터 그룹은 각각 별도의 서버 측 호출 작업으로 실행되어야 하며 응답 지연이나 회차 건너뛰기가 한 번도 발생하지 않아야 한다.
- **And** 관심 종목 호출이 실패해도 지수, 인기 종목과 포트폴리오 종목의 정상 결과는 표시되어야 한다.

#### AC-16 부분 화면 갱신

- **Given** 사용자가 포트폴리오 수량을 입력 중이고 새 실시간 데이터가 도착했으며
- **When** 클라이언트가 새 데이터를 반영하면
- **Then** 변경된 가격과 상태 영역만 갱신되어야 한다.
- **And** 입력 중인 수량, 키보드 포커스, 스크롤 위치와 선택 탭은 유지되어야 한다.

#### AC-17 분리형 서버·클라이언트 동기화

- **Given** 후속 버전에서 서버와 클라이언트가 분리되어 있고 서버 주기는 2초, 클라이언트 주기는 10초로 설정되어 있으며
- **When** 클라이언트가 연결되어 있지 않거나 10초 UI 동기화 사이에 있으면
- **Then** 서버는 2초 주기로 외부 데이터 수집을 계속해야 한다.
- **And** 클라이언트는 10초마다 서버의 최신 데이터를 읽되 외부 공급원을 직접 호출해서는 안 된다.

#### AC-18 분리형 주기 설정의 기본값 적용

- **Given** `server.poll_interval_seconds` 또는 `client.refresh_interval_seconds`가 없거나 숫자가 아니거나 정수가 아니거나 2보다 작은 정수로 설정되어 있고
- **When** 서버 또는 클라이언트가 시작되면
- **Then** 잘못된 설정에는 2초를 적용하고 입력값, 적용값과 보정 사유를 개발 로그에 기록해야 한다.

#### AC-19 응답 지연 표시와 복구

- **Given** `realtime.poll_interval_seconds=2`, `provider.request_timeout_seconds=5`이며 한 데이터 그룹의 외부 요청이 수집 시작 시각에 시작됐고
- **When** 해당 요청이 5초 안에 응답하지 않으면
- **Then** 시작 후 2초와 4초의 고정 조회 회차는 해당 그룹에 한해 건너뛰고 건너뛰기 횟수를 기록해야 한다.
- **And** 요청을 5초에 타임아웃으로 종료한 뒤 6초의 고정 조회 시각에 해당 그룹을 다시 요청해야 한다.
- **When** 클라이언트가 최신 상태를 읽으면
- **Then** 해당 그룹에 `응답 지연`, 마지막 정상 갱신 시각, 현재 조회 주기와 적용된 타임아웃을 표시해야 한다.

#### AC-20 관심 종목과 포트폴리오 한도

- **Given** `limits.watchlist_max_symbols=20`, `limits.portfolio_max_symbols=10`이 적용되어 관심 종목이 이미 20개 또는 포트폴리오 종목이 이미 10개 저장되어 있고
- **When** 사용자가 종목을 하나 더 추가하려고 하면
- **Then** 새 종목을 저장하지 않고 해당 최대 수와 기존 종목 삭제 방법을 안내해야 한다.

#### AC-21 배치 분할과 부분 성공

- **Given** `provider.max_symbols_per_request=10`, `provider.batch_size=10`이 적용된 상태에서 관심 종목 20개를 조회해 두 배치가 생성되었고
- **When** 첫 번째 배치는 성공하고 두 번째 배치는 실패하면
- **Then** 첫 번째 배치의 결과를 표시한 채 관심 종목 그룹을 `부분 성공`으로 표시해야 한다.
- **And** 성공·실패한 심볼 수 또는 배치 수와 마지막 정상 갱신 시각을 표시해야 한다.

#### AC-22 3회 재시도 실패와 그룹 단위 복구

- **Given** `realtime.poll_interval_seconds=2`, `provider.request_timeout_seconds=5`이며 한 데이터 그룹의 최초 요청이 타임아웃됐고
- **When** 이후 세 번의 재요청도 모두 타임아웃되면
- **Then** 요청은 수집 시작 후 0초, 6초, 12초, 18초에 시작되어야 한다.
- **And** 세 번째 재요청의 타임아웃이 확정되는 23초에 해당 그룹을 `실패` 상태로 전환하고 자동 조회를 중단해야 한다.
- **And** 다른 데이터 그룹의 자동 조회는 계속되어야 한다.
- **When** 사용자가 실패한 그룹의 `다시 시도`를 실행하면
- **Then** 해당 그룹의 실패 횟수와 중단 상태만 초기화하고 화면 상태와 다른 그룹의 상태를 유지해야 한다.
- **And** 해당 그룹은 다음 고정 조회 시각에 자동 조회를 재개해야 한다.
- **When** 사용자가 브라우저를 새로고침하면
- **Then** 모든 그룹의 실패 횟수와 중단 상태를 초기화하고 정상 조회를 다시 시작해야 한다.

#### AC-23 장시간 안정성 검증

- **Given** 최대 허용 종목 수와 `적용 자동 조회 주기`를 적용했고
- **When** 최소 1시간 또는 한 시장 세션 동안 안정성 테스트를 실행하면
- **Then** 프로세스 메모리 사용량, 그룹별 오류율, HTTP 429 발생 횟수와 연결 재수립 횟수를 기록해야 한다.
- **And** 처리되지 않은 예외로 애플리케이션이 종료되어서는 안 된다.

#### AC-24 기능별 최대 기간

- **Given** 사용자가 주요 지수 차트, 개별 종목 차트 또는 포트폴리오 분석의 기간 선택을 열었고
- **When** 선택 가능한 기간을 확인하면
- **Then** 주요 지수 차트는 최대 5년까지만 제공하고 개별 종목 차트와 포트폴리오 분석은 최대 10년까지 제공해야 한다.

#### AC-25 한도·배치·타임아웃 설정 변경

- **Given** 운영자가 다섯 한도·배치·타임아웃 설정을 모두 유효한 양의 정수로 변경하고 애플리케이션을 재시작했으며
- **When** 관심 종목·포트폴리오 추가와 데이터 그룹 조회를 수행하면
- **Then** 저장 한도, 공급원 1회 요청 최대 심볼 수, 요청 분할 크기와 요청 타임아웃에 각각 변경된 설정값을 적용해야 한다.
- **And** 클라이언트의 한도 안내와 응답 지연 상태에는 서버가 전달한 실제 적용값을 표시해야 한다.

#### AC-26 잘못된 한도·배치·타임아웃 설정 보정

- **Given** 다섯 설정 중 하나가 없거나 숫자가 아니거나 정수가 아니거나 1보다 작거나, 요청 분할 크기가 1회 요청 최대 심볼 수보다 크고
- **When** 애플리케이션이 시작되면
- **Then** 잘못된 값에는 해당 기본값을 적용하고 분할 크기는 적용된 1회 요청 최대 심볼 수 이하로 보정해야 한다.
- **And** 설정 키, 입력값, 적용값과 보정 사유를 개발 로그에 기록해야 한다.

#### AC-27 설정 축소 시 기존 데이터 보존

- **Given** 저장된 관심 종목 또는 포트폴리오 종목 수보다 작은 최대 한도 설정을 적용했고
- **When** 사용자가 해당 목록을 열거나 종목을 추가하려고 하면
- **Then** 기존 저장 항목을 삭제하지 않고 조회와 삭제를 허용해야 한다.
- **And** 신규 추가는 차단하며 현재 저장 수와 적용된 한도를 표시해야 한다.

#### AC-28 일반 조회 실패와 자동 재시도 횟수 분리

- **Given** 한 데이터 그룹의 자동 주기 조회 재시도 횟수가 2회이고
- **When** 사용자가 실행한 검색, 종목 상세 또는 과거 시계열 일반 조회가 요청 실패하거나 설정된 타임아웃을 초과하면
- **Then** 일반 조회에 단건 실패와 재실행 방법을 표시해야 한다.
- **And** 해당 데이터 그룹의 자동 주기 조회 재시도 횟수는 2회로 유지하고 그룹을 `실패` 상태로 전환해서는 안 된다.
- **And** 일반 조회 자체에 세 번의 자동 재시도를 실행해서는 안 된다.

#### AC-29 장 재개 시 고정 스케줄 원점 재설정

- **Given** 장 마감·휴장으로 자동 주기 조회가 중지되어 있고 `realtime.poll_interval_seconds=2`이며
- **When** 시스템이 장중 전환을 특정 시각에 감지하면
- **Then** 감지 시각을 새로운 데이터 수집 시작 시각으로 설정하고 해당 시각부터 2초 간격의 고정 조회 스케줄을 시작해야 한다.
- **And** 장 마감·휴장 동안 지나간 회차를 소급 실행하거나 기존 원점에 맞추기 위해 첫 조회를 지연해서는 안 된다.
- **And** 장 재개만으로 기존 그룹의 실패 횟수와 중단 상태를 초기화해서는 안 된다.

## 13. 개발 전 확인 사항

- Yahoo Finance가 각 시장·종목에 제공하는 시계열 기간과 간격을 검증한다.
- 데이터 이용 조건과 재배포 가능 범위를 확인한다.
- 한국 및 미국 시장의 종목·거래소·업종 매핑 규칙을 확정한다.
- 조정 종가와 배당 반영 방식이 시장별로 일관적인지 검증한다.
- 원화 환산에 사용할 환율 공급원과 휴장일 처리 방식을 확정한다.
- All Weather의 `DBC`가 데이터 공급원에서 올바른 원자재 자산으로 매핑되는지 확인한다.
- 초기 실시간 데이터 공급원이 현재 `적용 자동 조회 주기`를 지원하는지 부하·지연·이용 조건을 포함해 검증한다.
- 공급원이 `적용 자동 조회 주기`를 충족하지 못하면 검증 결과를 근거로 `realtime.poll_interval_seconds`를 늘릴지 대체 공급원을 선정할지 결정하고 변경 사유를 기록한다.
- 조회 주기를 변경하면 재시작 후 새 값을 `적용 자동 조회 주기`로 확정하고 1분 부하·스모크 테스트를 다시 실행한다.
- 배포 환경별 `realtime.poll_interval_seconds`, `provider.request_timeout_seconds`, `limits.watchlist_max_symbols`, `limits.portfolio_max_symbols`, `provider.max_symbols_per_request`, `provider.batch_size` 값과 변경 이력을 기록한다.
- KOSPI, KOSDAQ, NASDAQ, S&P 500을 포함한 주요 지수 그룹과 인기 종목, 관심 종목, 포트폴리오 종목을 `적용 자동 조회 주기`로 1분간 연속 호출하고 각 그룹의 요청 수, 평균·p95 완료 시간, 응답 지연과 회차 건너뛰기 횟수를 측정한다.
- 1분 검증 동안 응답 지연과 회차 건너뛰기가 모두 0회인 경우에만 해당 `적용 자동 조회 주기`의 부하 검증을 통과한 것으로 판정한다.
- 기본값과 변경된 설정값 각각에 대해 관심 종목·포트폴리오 한도, 공급원 요청당 최대 심볼 수, 배치 분할과 부분 성공을 검증한다.
- 다섯 한도·배치·타임아웃 설정의 누락, 비숫자, 비정수, 1 미만 값과 분할 크기가 요청 한도를 초과하는 경우의 폴백·보정 로그를 검증한다.
- 설정된 저장 한도를 기존 데이터 수보다 작게 변경해도 기존 항목이 보존되고 신규 추가만 차단되는지 검증한다.
- 최소 1시간 또는 한 시장 세션 안정성 테스트를 실행하고 메모리 사용량, 그룹별 오류율, HTTP 429와 연결 재수립 횟수를 기록한다.
- 고정 시각 조회, 설정된 타임아웃 동안의 회차 건너뛰기, 타임아웃 종료 후 처음 도래하는 고정 조회 시각의 재시도와 건너뛰기 횟수 기록을 검증한다.
- 세 번의 재시도 실패 후 그룹 중단, 그룹별 `다시 시도`의 선택적 초기화·화면 상태 보존과 브라우저 새로고침의 전체 초기화를 검증한다.
- 일반 조회의 요청 실패와 타임아웃이 자동 주기 조회의 재시도 횟수·그룹 중단 상태에 영향을 주지 않는지 검증한다.
- 장 마감·휴장 후 장중 전환 감지 시각을 새 스케줄 원점으로 사용하고 중지 기간의 회차를 소급 실행하지 않는지 검증한다.
- 선택한 UI 프레임워크가 전체 화면 재실행 없이 부분 갱신과 사용자 입력 상태 보존을 지원하는지 검증한다.
- 캐시 전략은 MVP 측정 결과를 근거로 후속 버전에서 결정한다.

위 확인 결과로 기능 제약이 발견되면 임의의 대체 데이터를 사용하지 않는다. 지원 시장, 기간, 간격과 계산 가정을 문서에 갱신한 뒤 구현한다.
